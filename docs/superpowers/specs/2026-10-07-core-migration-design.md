# Экономный перенос ядра Khitun Geo

Статус: подготовлено к согласованию. Реализация и язык пока не утверждены.

## Цель

Поэтапенно перенести вычисления координат в отдельное ядро, сохранив
точность, офлайн-работу и существующий интерфейс. Не совмещать перенос
с исправлением параметров СК или редизайном.

## Что установлено по исходникам

- Математика находится в JavaScript внутри `src/KhitunGeo/wwwroot/index.html`,
  а не в C#: `geodToEcef`, `ecefToGeod`, `helm`, `invHelm`,
  `fwdTM`, `invTM`, `datumToWgs`, `wgsToDatum`, `transformPoint`.
- C# — Windows Forms / WebView2 оболочка (`net8.0-windows10.0.19041.0`).
- `crsParams` и `detectZoneForPoint` читают элементы интерфейса.
  Это граница, которую нужно отделить от чистой математики.
- Уже существуют `tests/coordinate-systems.cjs` и наборы
  `crs-proj-controls.json`, `geoproj-global-controls.json`, `geoproj-holdout.json`.
  Текущий тестовый файл смешивает проверки координат и интерфейса.
- Проверки PROJ в существующем наборе используют допуски 0.002 м
  по плану и 0.003 м по высоте. Остальные допуски сохраняются из их тестов.
- Rust/Cargo не найдены в PATH проверенной среды.

## Варианты

1. Rust + небольшая C ABI библиотека — предлагаемый вариант нового ядра.
   Windows-оболочка вызывает пакетный расчёт через C#; интерфейс остаётся прежним.
   Требуется отдельная сборка и упаковка native DLL.
2. C++ + C ABI — аналогичная интеграция; имеет смысл при наличии
   нужного C++ кода или библиотек. Такой причины пока не установлено.
3. Только выделение JavaScript-модуля — самый маленький первый шаг,
   полезный при любом последующем выборе языка, но сам по себе не новый язык.

## Последовательность

1. Выделить существующее тестовое окружение и фиксированную проверку математики
   без запуска тестов всего интерфейса. Не менять ожидаемые результаты.
2. Снять исходный результат фиксированного набора. Известное расхождение
   МСК-164 → ГСК-2011 учитывать отдельно: совпадение со старым кодом
   доказывает эквивалентность переноса, но не геодезическую правильность.
3. Вынести чистую математику в `coordinate-core.js` без изменения формул;
   параметры СК и зон передавать явно из адаптера интерфейса.
4. Первый вертикальный срез нового ядра: WGS-84 ↔ ГСК-2011 географическая,
   включая отрицательные, нулевые и положительные высоты и обратный проход.
   Сравнивать JavaScript и новое ядро автоматически на фиксированных данных.
5. После прохождения среза переносить проекции и остальные датумы,
   используя те же определения СК и существующие эталоны.
6. Подключить пакетный вызов через Windows-оболочку, проверить сборку
   и ошибки интеграции. Переключать рабочие вычисления только после проверки.

## Контракт и ограничения

- Вход: массив числовых троек и явные параметры исходной/целевой СК,
  режима зоны и префиксов. Ядро не читает DOM, файлы проекта и настройки UI.
- Сохранить действующий порядок осей: X/N, Y/E; для географических — B/L.
- Разделять эллипсоидальную высоту математического преобразования и
  пользовательскую высоту/глубину, которую прикладной режим может сохранять.
- Нечисловые и бесконечные значения возвращают ошибку; ошибки не заменяются нулями.
- Расчёт не меняет входные точки. Таблица обновляется только после
  успешного результата всего запрошенного пакета.
- Новый код не должен молча откатываться на старое ядро при ошибке.
- Параметры спорной МСК-164 нельзя объявлять эталонными только по старому результату.
- Эталонные файлы не перегенерируются по результатам нового ядра.
- Полные повторные проверки вне фиксированного набора нужны только при
  изменении формул, параметров СК или выявленном отличии поведения.
- Перенос только математики не устраняет зависимости оболочки от .NET/WebView2
  и сам по себе не гарантирует уменьшение установщика или RAM.
- GitHub-публикация, установщик, DXF/DWG, новый дизайн и прочие пункты
  будущего обновления не входят в этот первый этап.

## Приёмка

Чистый модуль работает без UI; фиксированные эталоны проходят с прежними
допусками; старое и новое ядра сравниваются автоматически; исходные данные,
оси, зоны и политика высот сохраняются. Проверка Windows-интеграции
отмечается отдельно от проверки математики.

## Решение перед реализацией

Подтвердить Rust как целевой язык и приведённые границы первого этапа.
После этого составить краткий план конкретных изменений и выполнять
последовательно, без параллельных агентов.
